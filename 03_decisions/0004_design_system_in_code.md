# 0004 — design system in code

<!-- status: proposed | accepted | superseded | rejected — only the owner flips proposed → accepted -->

## context
[[ui_design_system]] produced the v1.0 design system, **Modern Felt**, in Claude Design ([artifact](https://claude.ai/artifact/684t9mutghLZBVsCFB1ydy), version of 2026-09-23 07:30 UTC). Its ground rules are [[design_system_ground_rules]] (UI-R1–R36). It went through three `design-reviewer` rounds. On 2026-09-24 the owner froze it: **"what we have right now is enough"**. The remaining gaps are fixed during implementation, not in further Claude Design rounds. They are listed in [[design_system_ground_rules]] → *known gaps — fix in implementation*.

What Claude Design produced, and its shape:
- **`tokens.json`**: three tiers (OKLCH primitives → semantic roles → component tokens), dark theme only. It uses the Claude Design *list* format (`{"tokens":[{name, value, usage}]}`), not W3C DTCG.
- **`components/bundle.js`**: 20 React 18 components. It's one classic script that uses `React.createElement` and assigns the global `window.Felt`. There are no modules, no JSX and no types in the code itself. `index.d.ts` describes the API separately.
- **`components/bundle.css`**: about 27 KB of plain CSS with `mf-` class names, reading tokens as CSS custom properties. The `tokens.css` it reads is generated by the Claude Design page and was not downloaded.
- **Fonts**: six Barlow / Barlow Semi Condensed woff2 files plus the OFL licence.
- **Previews and documentation**: 17 + 2 screen previews, Table stress tests and a README "brand book".

The code side is fixed by [[0003_monorepo_structure_and_tech_stack]]: Turborepo + pnpm, TypeScript only, `apps/web` is React + Vite, and `engine`/`protocol` are consumed from TS source.

Forces:
- AI agents build most of the UI. They need one place that says what the tokens and components *are*, and tests that fail when a rule in the spec breaks (contrast, layout overlap, full digits on buttons, and so on).
- The design system must extend later: v1.1 lobbies, v2.0 wallet, v3.0 verification, and an eventual light theme. This works through new semantic roles, not a redesign.
- Claude Design is still useful for exploring later versions' screens. Losing that path would be a cost.
- The pot-preset and minimum-raise logic now sits inside a UI bundle (`Felt.potPresets`). Rules like minimum raise belong to the engine (R20–R26 in [[nlhe_cash_game_rules]]); the engine currently exposes `applyAction` but no "legal actions / min raise-to" query.

**Assumption:** the DesignSync tool, which syncs a local component library with claude.ai/design design-system projects, works with this system. Modern Felt is an Artifact made from the *Design System* type in Cowork. Whether DesignSync treats it as a design-system project has not been checked. DesignSync is only used through the `/design-sync` skill, which the owner starts.

## options considered

### A. Source of truth
1. **The repo is canonical; Claude Design is the frozen v1.0 reference.** Tokens and components are ported once into `packages/ui` and owned by code from then on. Claude Design is used again only to explore new screens for later versions. Those explorations are ported the same way, and the system can be re-synced *from* code so it stays a browsable catalogue. **Pros:** one truth that tests can enforce; agents work in TypeScript. The known gaps are fixed where they will actually run. **Cons:** the Claude Design catalogue drifts unless someone re-syncs it; a designer-led change becomes a port, not a pull.
2. **Claude Design is canonical; code is regenerated from its bundle on every change.** **Pros:** design changes arrive in one step. **Cons:** the bundle is an untyped global script and fixes made in code would be overwritten. The owner has just ended the back-and-forth that this option would require. Tests would run against generated code nobody owns.
3. **Split: tokens canonical in Claude Design, components canonical in code.** **Pros:** colour and type tweaks stay designer-editable. **Cons:** two sources of truth. A token change in Claude Design can silently break a contrast pair that code tests assume. Every sync needs a review anyway, so this is option 1 with extra steps.

### B. How the components get into the repo
1. **Port `bundle.js` into typed TSX components.** One file per component, props taken from `index.d.ts`, behaviour kept, known gaps fixed as they're ported. **Pros:** typed, tree-shakable, testable, reviewable. **Cons:** a few days' porting work; a porting mistake could reintroduce a bug the review already cleared. Mitigated by the screenshot and geometry tests below.
2. **Vendor `bundle.js` as is and wrap it.** **Pros:** fastest. **Cons:** relies on a global `window.React`/`window.Felt`, has no types and no tree-shaking, and every fix means editing minified-style generated code. Rejected.

### C. Styling
1. **Plain CSS with custom properties, ported from `bundle.css`.** Keep the `mf-` prefix; generate `tokens.css` from the token file. **Pros:** matches the source 1:1, no runtime, no new tooling, and theming (the future light theme) is just re-pointing custom properties. **Cons:** global class names, which the prefix keeps manageable.
2. **CSS Modules.** **Pros:** scoped names. **Cons:** a rename pass over every class for little gain in a single-product repo.
3. **Tailwind / CSS-in-JS.** **Pros:** popular with agents. **Cons:** a rewrite of every style, a second token pipeline, and runtime cost for CSS-in-JS. Rejected.

### D. Workshop and visual tests
1. **Ladle for component stories, plus Playwright for screenshot, geometry and accessibility tests against those stories.** Ladle is a Vite-native story runner (**from memory, unverified** — confirm version and React 18 support at implementation). **Pros:** reuses the Vite toolchain; each Claude Design preview becomes a story; Playwright can repeat the reviewer's checks (overlaps at 360×640, 150%/200% text, insets) and run axe-core. **Cons:** one more dev dependency.
2. **Storybook + test-runner.** **Pros:** the best-known option. **Cons:** a heavier toolchain and a slower install for a single-product repo.
3. **No workshop; Playwright against `apps/web` screens only.** **Pros:** the fewest tools. **Cons:** components can't be tested in isolation, and states that are hard to reach in a live game (side pots at 8, void hand) need test fixtures inside the app.

## decision
**A1 + B1 + C1 + D1.**

- New workspace package **`packages/ui`** (`@poker/ui`), consumed from TS source like `engine`/`protocol`. It holds:
  - `tokens/tokens.json`: **the canonical token file**. It is kept in Claude Design's list format so a later re-sync to the design system catalogue is a copy, not a conversion. A small build script generates `tokens.css` (custom properties) and a typed `tokens.ts`.
  - `src/`: one TSX component per `index.d.ts` export (Card, BetMarker, Seat, Table, ActionBar, BetSizer, SeatSheet, …), with plain CSS ported from `bundle.css`.
  - `fonts/`: the six woff2 files plus `OFL-Barlow.txt`, self-hosted.
  - `format.ts`: `fmt` (abbreviated: seats, bet markers, pot only) and `full` (everything the player acts on).
- **Rules stay in the engine.** A new pure engine query, e.g. `legalActions(state)`, returns to-call, min raise-to, max raise-to and whether raising is reopened. The UI's pot/preflop presets are computed from it (formula per UI-R21) and never re-implement the minimum-raise rules.
- **Claude Design's Modern Felt is frozen as the v1.0 visual reference.** Later versions may explore new screens there. Any change becomes code through a normal PR that keeps every UI-R test green. Re-syncing the catalogue from code (DesignSync via `/design-sync`) is optional housekeeping, not a gate.
- **Tests that enforce the spec in CI** (Vitest + Playwright):
  - a contrast test over every token pair the README lists
  - full digits on action controls (UI-R16)
  - the preset formula and All-in merge (UI-R21)
  - no-overlap geometry for the 9-seat stress cases at 360×640, at 100/150/200% text, with and without 47/34 insets (UI-R17, R18, R28–R31)
  - axe-core on every story
  - screenshot baselines at 360×640, 390×844, 768 and 1280
  - a banned-words check over product copy (UI-R1, R2)
- **Known gaps** listed in [[design_system_ground_rules]] are fixed during the port and each gets a test. They are part of the definition of done for `packages/ui`.

## consequences
- There is one source of truth that CI enforces, and agents build screens by composing `@poker/ui` components against a typed API.
- The port is real work, several focused sessions. The screenshot and geometry tests are what keep it faithful to the reviewed design.
- The Claude Design catalogue will drift from the code unless it's re-synced. That's accepted: the spec and the tests are what bind, not the catalogue.
- Keeping the token file in Claude Design's list format (not DTCG) makes it easy to hand back to Claude Design. It also means a converter would be needed if a DTCG tool (Figma, Style Dictionary) ever enters the picture.
- The engine gains a `legalActions` query. That's useful to the server too, which must reject illegal actions (UI-R22: stale amounts are rejected server-side).
- A light theme later is a second value set in `tokens.json` plus re-pointed semantic roles; components don't change.

## revisit when
- A designer or the owner wants to iterate visually faster than code PRs allow. Then reconsider A3, or a scripted import from Claude Design.
- DesignSync proves unable to read or write this system, or proves reliable enough that designer-first becomes cheap.
- A second product surface (a native app per [[0003_monorepo_structure_and_tech_stack]]'s revisit list) needs the tokens. Then consider DTCG plus a multi-platform build.
- The Playwright screenshot suite becomes flaky or too slow for CI (> ~5 min).
